Quick start · carelink-bridge

Get the bridge running.

The bridge signs into Medtronic’s CareLink service the way the official app does and copies pump and sensor readings into a Nightscout site you run. The user guide budgets about fifteen minutes for the setup itself.

Requirement

Node.js 20 or newer

The package declares engines.node >=20.0.0. CI runs on Node 20 and 22, so anything outside that range is untested.

Requirement

A Medtronic pump on CareLink

Anything that uploads to CareLink. The 780G with a Guardian 4 or Simplera sensor is the combination actually exercised by the maintainer’s own setup.

Requirement

Somewhere always on

A VPS or a machine that stays awake. The installer is idempotent and there is a hardened systemd unit in the repository.

# verbatim from the README of NovaLux12/carelink-bridge git clone https://github.com/NovaLux12/carelink-bridge.git cd carelink-bridge npm install && npm run build cp .env.example .env # then fill in CARELINK_USERNAME, CARELINK_PASSWORD, API_SECRET, NS npm run doctor # pre-flight check npm run login # one-time OAuth login npm start # fetch loop
Then read USER-GUIDE.md for the full stack — Nightscout, the bridge, and the tunnel. The repository also ships ARCHITECTURE.md SECURITY.md CONTRIBUTING.md ROADMAP.md CHANGELOG.md and eight architecture decision records under docs/adr/.
Already have Nightscout data?

Two stdlib-only Python tools

Neither talks to Medtronic. They read an existing Nightscout instance and turn history into a weekly report or an SVG chart. Python 3.9 and up; CI currently exercises 3.11 to 3.13.

ns-reports

Weekly numbers

Averages, time in range, lows and highs, basal/bolus split, per-day breakdowns. Text or JSON.

ns-cgm-graph

SVG charts

Recent CGM history as clean SVG, for reports or dashboards. No matplotlib, no browser, no dependencies.

Architecture · sensor to sentence

How the pieces fit.

Four repositories, one direction of data flow. Everything reads or writes Nightscout, which is the source of truth; nothing writes back to CareLink and nothing touches dosing.

Your machine

Everything from step 1 to 5

The bridge, the MCP server and both Python tools run on hardware you control, pointed at a Nightscout instance you host. None of them phone home.

Maintainer-run

Step 6 only, and only during the pilot

The overnight brief and the clinic-ready PDF are composed by the maintainer, optionally, during the pilot. That is the one piece you do not run yourself.

Explicitly not here

Anything that doses

No closed-loop control, no new alarm sources, and nothing that replaces the official CareLink safety notifications. A data bridge that starts making treatment decisions stops being a data bridge.

Agent layer · nightscout-mcp · private preview

The tool surface, and why it is shaped that way

Model Context Protocol server for Nightscout60 read · 6 gated writes

An agent asking questions about your glucose data should be boring and read-only. Everything interesting about this server is in what it refuses to do by default.

Default posture

Writes dry-run

All six write tools simulate unless a literal confirm flag is present on the same call. There is no ambient authorisation and no session that stays open.

Default posture

Two-token access control

A read token unlocks the sixty read tools. A separate write token, plus a master switch, unlocks the six writes. Full-admin is refused outright.

Default posture

Every write is on disk

Confirmed writes land in a 0600 JSONL audit log on your own filesystem. Grep it, ship it to a clinician, delete it — it is your file.

Two transports

stdio for a desktop assistant, streamable HTTP for agent clients. Binds other than loopback are refused unless you opt in explicitly.

Validator-safe logging

Error paths log exception types, never messages, so a rejected token cannot leak into the log. A canary test enforces it.

Fails at startup, loudly

The launch banner names the two reasons writes would fail — careportal disabled, or runtime still loading — before an agent tries and fails silently.

Security · model and disclosure

What this thing can and cannot do.

This is health data. The threat model is written down per repository, and the disclosure route is RFC 9116 rather than a mailbox someone has to remember to check.

Boundary

No telemetry, anywhere

Nothing is sent back to the maintainer. The bridge posts to your Nightscout and nowhere else. There is no analytics on this site either — it ships zero JavaScript, so there is nothing to phone home with.

Boundary

Credentials stay local

Tokens are written atomically with 0600 permissions and are wiped only on a permanent authentication failure, never on a transient one.

Boundary

Millimoles converted at source

CareLink and Nightscout trade in mg/dL; UK practice is mmol/L. The conversion happens at the ingest site, because getting it wrong downstream makes looping clients over-deliver insulin.

Out of scope

No dosing, ever

Research and educational tooling. Not a medical device, not FDA approved, not affiliated with or endorsed by Medtronic. Every treatment decision stays with the human and their diabetes team.

Report a flaw

security.txt, per RFC 9116

Served at /.well-known/security.txt and /security.txt. Prefer GitHub private vulnerability reporting on the repository where the flaw lives.

Report a flaw

Do not open a public issue

A public issue leaks the detail to everyone at once. Private advisory or email first, always.

Known gaps, stated plainly: the repository does not ship a code of conduct or CODEOWNERS, and the two Python tools claim Python 3.9 and up while CI only exercises 3.11 to 3.13. ns-reports is versioned by tag and has no GitHub release object. These are being fixed, not hidden — check the repositories rather than take this page’s word for it.

Contributing · issues, patches, reviews

How to help.

This is one person’s project, so the useful contributions are specific ones: reproduce something, fix a doc, test on hardware nobody else has.

Most useful

Test on your hardware

The bridge is exercised on one pump and one sensor combination. Anyone with a different Medtronic setup who can report what does and does not work removes a whole class of blind spot.

Most useful

Report upstream, not downstream

Some defects belong to domien-f/carelink-bridge. A fix traced upstream survives the upstream project waking up; a patch only here gets stranded.

Useful

Issues before pull requests

Public issues for bugs and features — they move faster than email and leave a trail. The bridge ships a CONTRIBUTING.md; read it first.

Useful

Architecture records

Eight ADRs exist for the bridge. New decisions deserve the same treatment: what was decided, and what would reverse it.

Honest gap

No code of conduct yet

There is no CODE_OF_CONDUCT.md in any repository. Until one exists, the maintainer’s rule is simple: be decent, and assume good faith.

Private by default

Do not file a security flaw publicly

Use security.txt or GitHub private advisories. A public issue spreads the detail before anyone can patch it.

Reference · the vocabulary

Words this project keeps using.

Half of what looks like jargon here is two acronyms and a units question. All of it is defined in the repositories too.

What is the Model Context Protocol?

An open standard that lets an assistant call tools exposed by a program. nightscout-mcp is a Nightscout server in those terms: sixty read tools, six write tools.

What is an ADR?

An architecture decision record — a short dated note recording why a technical decision was taken and what would reverse it. The bridge publishes eight under docs/adr/.

Why does the mmol/L conversion matter so much?

The UK measures glucose in mmol/L; CareLink and Nightscout trade in mg/dL. Mixing them makes looping clients over-deliver insulin, so the bridge converts at the ingest site rather than trusting each consumer to get it right.

What are GMI, TIR and CV?

Three standard summary numbers. GMI estimates HbA1c from mean sensor glucose. TIR is the share of readings between 3.9 and 10.0 mmol/L. CV is variability relative to the mean, with under 36% the usual clinical target.

What is a CGM SGV?

A sensor glucose value: one reading from a continuous glucose monitor, usually timestamped and interpolated by the platform rather than read straight off the sensor.

What is Nightscout?

An open-source remote monitor for glucose data, maintained by the #WeAreNotWaiting community, that you host yourself. Every Loopwise tool reads from your Nightscout instance, or writes to it, and nowhere else.

What is CareLink?

Medtronic’s cloud service. Your pump and sensor upload to it; the bridge signs in the way the official app does and copies the new data across.

What does the BLE detection fix do?

Device discovery over Bluetooth Low Energy. The fix was carried from upstream pull request #2 by @terminalcommand and landed here with a regression test, because upstream has been quiet.

Is this affiliated with Medtronic?

No. It is an MIT-licensed community fork, not affiliated with, endorsed by, or sponsored by Medtronic. It builds on domien-f/carelink-bridge, itself inspired by the Nightscout community’s minimed-connect-to-nightscout. If upstream wakes up, the fixes fold back.
