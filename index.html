Repository 01 · MIT · Community fork

carelink-bridge

github.com/NovaLux12/carelink-bridge

Pulls Medtronic pump and CGM data into Nightscout automatically by signing into CareLink the way the official app does. A community fork kept alive while upstream is quiet — including the BLE fix for 780G, Guardian 4 and Simplera that un-breaks empty-data nights.

Safety

mmol/L converted at the source

Non-US CareLink accounts are converted to mg/dL at the SGV assignment site. Without this, downstream looping clients would over-deliver insulin.

Safety

Atomic, locked-down credentials

Login tokens written atomically with 0600 permissions — no world-readable window — and wiped only on truly permanent auth failure, never on a blip.

BLE device detection fix

Cherry-picked upstream PR #2 with a regression test: fixes empty-data issues on 780G, Guardian 4 and Simplera CGM devices.

npm run doctor

"Why is no data showing up" becomes one command: env vars, CareLink reachability, Nightscout reachability, token validity — non-zero exit to gate deploys.

Stale-data watchdog

Tracks the last successful fetch, warns after 15 quiet minutes, optionally POSTs a webhook — a silent bridge never stays silent.

Status-aware retries

Capped exponential backoff with jitter that honours Retry-After and classifies failures. Rationale published in four ADRs.

One-hour deploy

Hardened systemd unit, idempotent install script, Nightscout + Mongo + Cloudflare-tunnel compose stack. Live within an hour of first pump data.

Three login strategies

OAuth, headless browser, and partner fallbacks across known API versions — because Medtronic changes things and nights do not wait.

Alarms surfaced, not sent

CareLink alarms surface as Nightscout devicestatus with priority-1 codes always logged. Deliberately never relayed as treatments.

What you get

Three things, every week.

No dashboard to learn. No SaaS login. You get a brief, a PDF, and a paper trail — and you stay in charge of every decision.

01 · Each morning

A live trace read

A one-paragraph morning brief in plain English, pointing at the parts of the overnight trace that warrant a second look. No decisions made for you — flags only.

02 · Each week

A weekly PDF

One page you can email to your diabetes team: averages, variability, time in range, lows, highs, basal/bolus split, per-day breakdowns. Every number traceable to its source data.

03 · Always

An audit trail

Every confirmed write lands in a 0600 JSONL log on disk. Read it, grep it, hand it to a clinician. Nothing happens without a record.

Repository 02 · MIT · Single-operator fork · Private preview

nightscout-mcp

Model Context Protocol server for Nightscout

Lets Claude query personal Nightscout data — CGM history, treatments, ISF/CR derivations, AGP/GRI metrics, loop status — and, only with explicit opt-in, log treatments back. Every write is gated, audited, and reversible in feeling if not in fact.

Safety

Confirm-gated writes

All 6 write tools dry-run by default. Only a literal confirm flag on the same call posts — every confirmed write lands in a 0600 JSONL audit log.

Safety

Two-token access control

Read token unlocks 60 read tools; a separate write token plus a master switch unlock the 6 writes. The full-admin secret is refused outright.

60 read tools

v1, v2 and modern v3 search/history APIs — plus analytics, pattern detection, AGP/GRI and AAPS/loop status.

Token-leak-proof logging

Error paths log exception types, never messages — validators embed rejected input in their strings. Enforced by a canary test.

Speaks HTTP too

Stdio for Claude Desktop, streamable-HTTP for OpenClaw and other agent clients — non-loopback binds refused unless opted in.

Warns before you do

Startup banner surfaces Nightscout server state: careportal disabled, runtime still loading — the two reasons writes would fail.

Repositories 03 + 04 · MIT · Zero dependencies

The reporting toolkit.

ns-reports · ns-cgm-graph

Two small, sharp Python tools — stdlib only, tested on 3.11–3.13, CI on every push — that turn Nightscout history into numbers and pictures. They are the working seed of the clinic-reports bet: the metrics and visuals our Claude layer will compose into shareable reports.

ns-reports

weekly generator · text + JSON · pipx / pip / clone-and-run

Fetches 7 days of entries and treatments, prints the week that was: averages, variability, time in range, lows and highs, basal/bolus split — plus per-day breakdowns. --json emits one object agents can consume directly.

$ ns-reports --days 7 7-day · 2009 readings avg 8.7 mmol/L · sd 3.2 · GMI 7.2% · CV 36% time in range 65% · 96 lows · 610 highs basal 50.0 U · bolus 120.5 U # illustrative figures from the project README

ns-cgm-graph

SVG charts · any window · pipx / pip / clone-and-run

Renders recent CGM data as a clean SVG — hours or days at a flag — ready to embed in a report, a dashboard, or a morning brief. No matplotlib, no browser, no dependencies at all.

$ ns-cgm-graph --hours 72 --out cgm-72h.svg fetched 864 readings from Nightscout wrote cgm-72h.svg (12 KB, stdlib only) # the hero trace above is drawn the same way

Future plans

What's next.

The bridge follows a phased, opt-in roadmap — nothing ships until the phase before it is solid. The Claude layer is where the startup bet goes, and the toolkit is its foundation.

Now

In progress · gated on real data
  • Real-data validation against a live 780G account when the pump arrives — deferred payload items verified, not assumed.
  • Reliability (v0.3): circuit breaker for CareLink outages, persistent fetch-state, refresh-before-expiry.
  • Observability (v0.4): structured JSON logs plus a Prometheus /metrics endpoint.

Next — the Claude layer

The startup bet · built on Claude
  • Overnight-trace agent: reviews the night via the MCP tools, drafts a morning brief with pattern flags for user and clinic.
  • Clinic-ready reports: toolkit metrics + graphs composed into shareable PDFs a diabetes team can read.
  • Repo triage automation: faster, safer answers on community issues across all four repos.

Later

Proposed · low priority until the core is boring
  • Distribution: single static binary, Docker image, Home Assistant add-on.
  • Multi-account / caregiver mode and a mock CareLink server for testing.
  • Library split: client + uploader + daemon once the API settles.
Explicitly out of scope: closed-loop insulin dosing, new alarm sources, anything replacing official CareLink safety notifications. A data bridge that starts making treatment decisions stops being a data bridge.
Frequently asked

Honest answers to the questions we keep getting.

If yours isn't here, mail the maintainer — the inbox is read by a person.

What exactly is Loopwise Health?

A small, maintainer-run project that keeps the open diabetes plumbing alive — a Medtronic CareLink-to-Nightscout bridge, a Nightscout MCP server, and a zero-dependency reporting toolkit — and layers a Claude-powered brief, report and triage workflow on top. See the pipeline section above for the full picture, and the built in the open strip for what's actually verifiable.

Is it safe? Does it dose insulin for me?

No. No dosing decisions are ever delegated to software — the bridge, the MCP server and the Claude layer all work on data, not control. The stack is research and educational tooling only: not a medical device, not FDA approved, and explicitly out of scope for any closed-loop behaviour (see the roadmap's scope note). Every treatment decision stays with the human operator and their diabetes team.

Which pumps and CGMs does the bridge support?

Medtronic 780G pumps paired with Guardian 4 or Simplera sensors, fetched via CareLink the way the official app does. The community BLE fix for those three devices is the active testing surface. Other CareLink-compatible models should work but aren't in the regression suite. Closed-loop control of any kind is out of scope.

How much does it cost?

Free. All four repos — carelink-bridge, nightscout-mcp, ns-reports and ns-cgm-graph — are MIT-licensed. You only pay for the hardware you already own (pump, CGM) and the small VPS you choose to host the bridge on. There's no paid tier, no subscription, and no telemetry sent back to us.

How do I get started?

Read the bridge docs on GitHub — the USER-GUIDE walks you from a fresh VPS to a working Nightscout + bridge + Cloudflare tunnel stack in about an hour. Run npm run doctor at any time to check the pipe is healthy. If you hit something the docs don't cover, mail the maintainer.

Can my clinic use the reports?

Yes — that's the whole point of the clinic-reports bet on the roadmap's "next" phase. The toolkit already emits machine-readable JSON plus per-day breakdowns, so a clinic can audit every number behind the visual. The polished, shareable PDF wrapper is the deliverable we're building next, not something shipping today.

Where does my data live?

On your Nightscout instance, which you host — the bridge posts there and nowhere else. There is no telemetry back to us, no analytics on this site, and the MCP server reads your instance on your machine. Confirmed writes are logged to a 0600 JSONL file on your own disk.

Are you affiliated with Medtronic?

No. The bridge is an MIT-licensed community fork, kept alive while upstream is quiet. Not affiliated with, endorsed by, or sponsored by Medtronic — their trademarks belong to them. If upstream wakes up, we fold our fixes back.

Help me help you

What to include in a message

For bugs: which repo, the exact command you ran, what you expected, what happened, and a copy of the relevant log line (redact tokens first). For clinic or partnership enquiries: a couple of lines on your team and what you'd want to see in a report.

Where else

Open a GitHub issue

For bugs and feature requests, opening an issue on the relevant repo is usually faster and gives the next maintainer the context they need. Email is best for things that shouldn't be public — medical details, partnership talks, or security disclosures.
